title: "Calendar sync"
description: "Connect a Google or Microsoft 365 calendar in one consent screen, or any calendar with a secret ICS address — upcoming meetings import automatically and retain their source."
---

Connect your calendars once and Vexa keeps your **Upcoming** meetings in sync: every calendar event
with a Meet/Zoom/Teams link becomes a [planned meeting](/core/meetings#the-lifecycle--one-meeting-one-row),
and the bot [auto-joins](/core/meetings#auto-join--scheduled-means-the-bot-comes) each one at start
time.

Three ways to connect a calendar:

- **Google Calendar (recommended)** — one consent screen, read-only, no secret address to find.
  See [Connect Google Calendar](#connect-google-calendar) below.
- **Microsoft 365 / Outlook.com (recommended)** — one consent screen against Microsoft Graph,
  read-only, no secret address to find. See [Connect Microsoft 365](#connect-microsoft-365) below.
- **Any other calendar (ICS)** — a Google or Microsoft account an admin has not enabled OAuth for,
  or any other provider — off a **secret ICS address** your calendar provides. See
  [Connect with a secret ICS address](#connect-with-a-secret-ics-address) below.

You can connect up to **ten** calendars total (Google + Microsoft + ICS combined), each with its
own auto-join policy and bot name — see the [Calendar API](/api/calendar) for the endpoints.

## Connect Google Calendar

Open **Add Bot** → the **Calendar** tab, and click **Connect Google Calendar** — it's the primary
action there, above the ICS fallback. Google shows its own consent screen naming exactly one
permission — read-only access to your calendar — and redirects back to Vexa's
`/calendar/google/callback` page, which finishes the connection and hands you back to the same
Calendar tab, already connected. No secret address, no copy-paste, no other field to fill in.

If Google's consent screen is declined, or the connection fails, the callback page names the exact
reason (Google's own rejection, or "you declined the consent screen") and a **Back to Calendar**
button that returns you to the same tab to try again.

A connection whose access has been revoked or expired shows **Reconnect needed** instead of a
silent sync failure — click **Reconnect** to repeat the same consent flow and clear it.

<Info>
**What Vexa can see:** the `calendar.readonly` scope (events, and the calendar list so Vexa can
offer more than your primary calendar later) — never write access, never another person's
free/busy, never any Google product besides Calendar. Revoke it anytime from
[myaccount.google.com/permissions](https://myaccount.google.com/permissions); Vexa detects the
revocation on the next sync and shows **Reconnect needed** instead of failing silently.
</Info>

### Self-hosting: Google Cloud Console setup

DB-30's OAuth flow needs its own Google Cloud OAuth client — a **different** one from the
dashboard's own "Sign in with Google" client (a different consent: this one asks for calendar
access, sign-in asks for none). One Google Cloud OAuth client **may** serve both purposes if both
redirect URIs are registered on it; most self-hosters find it simpler to keep them separate so a
calendar-scope change never touches sign-in.

1. [Google Cloud Console](https://console.cloud.google.com/apis/credentials) → **Create
   credentials → OAuth client ID**.
2. **Application type: Web application.**
3. Under **Authorized redirect URIs**, add your dashboard's callback page — exactly the value you
   will set as `GOOGLE_CALENDAR_REDIRECT_URI` (below), e.g.
   `https://dashboard.example.com/calendar/google/callback`. Google refuses the consent screen
   with `redirect_uri_mismatch` if these do not match byte-for-byte.
4. On the **OAuth consent screen**, add the scope
   **`https://www.googleapis.com/auth/calendar.readonly`** (Google Calendar API → read-only). If
   the consent screen is in **Testing** mode, add your own Google account as a test user, or
   publish the app for a production deployment.
5. Copy the **Client ID** and **Client secret** into admin-api's environment:

```bash
GOOGLE_CALENDAR_CLIENT_ID=xxxxxxxxxx.apps.googleusercontent.com
GOOGLE_CALENDAR_CLIENT_SECRET=xxxxxxxxxx
GOOGLE_CALENDAR_REDIRECT_URI=https://dashboard.example.com/calendar/google/callback
CALENDAR_TOKEN_ENCRYPTION_KEY=$(python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())")
```

`CALENDAR_TOKEN_ENCRYPTION_KEY` is unrelated to the Google client — it is the AES-256-GCM key
admin-api encrypts every stored Google refresh token with (`token_cipher.py`), at rest, never in
the clear. It must be standard base64 of exactly 32 raw bytes; admin-api refuses to start the
Google routes on anything shorter, longer, or not valid base64. Losing or rotating it makes every
previously-stored Google connection unreadable, which surfaces as the same **Reconnect needed**
state a revoked grant produces — never a silent failure.

Unset any of the four keys and the three Google routes
(`GET /user/calendars/google/authorize`, `POST /user/calendars/google/exchange`, and the internal
`POST /internal/calendars/{id}/google-token`) answer a typed `503` naming exactly what's missing;
the ICS calendar surface below is completely unaffected.

## Connect Microsoft 365

The Microsoft Graph connector exists at the API level today
(`GET`/`POST /user/calendars/microsoft/{authorize,exchange}`, below) — the dashboard's own
**Connect Microsoft 365** button is a separate, not-yet-shipped piece of dashboard work, so it does
not appear next to **Connect Google Calendar** on the Calendar tab yet. Once it ships, the flow will
be the same shape as Google's: one consent screen naming exactly one permission — read-only access
to your calendar — and a redirect straight back into Vexa, connected. No secret address, no
copy-paste.

<Info>
**What Vexa can see:** the `Calendars.Read` scope (events on your default calendar and any others
you name) — never write access, never another person's free/busy, never any Microsoft 365 product
besides Calendar. Remove Vexa's access anytime from
[myaccount.microsoft.com](https://myaccount.microsoft.com/); Vexa detects the revocation on the
next sync and shows **Reconnect needed** instead of failing silently.
</Info>

### Self-hosting: Azure app registration setup

DB-32's OAuth flow needs its own Azure app registration — a **different** one from any dashboard
sign-in client (a different consent: this one asks for calendar access, sign-in asks for none).

1. [Azure Portal → App registrations](https://portal.azure.com/#view/Microsoft_AAD_RegisteredApps/ApplicationsListBlade)
   → **New registration**.
2. **Supported account types:** pick **Accounts in any organizational directory and personal
   Microsoft accounts** unless your deployment is restricted to one Azure AD tenant — this is what
   lets `MICROSOFT_CALENDAR_TENANT_ID` stay at its default, `common`.
3. Under **Redirect URI**, platform **Web**, add your dashboard's callback page — exactly the value
   you will set as `MICROSOFT_CALENDAR_REDIRECT_URI` (below), e.g.
   `https://dashboard.example.com/calendar/microsoft/callback`. Microsoft refuses the consent
   screen if these do not match byte-for-byte.
4. Under **API permissions**, add **Microsoft Graph → Delegated permissions → `Calendars.Read`**
   and **`offline_access`** (offline_access is what earns a refresh token — without it Microsoft's
   v2 endpoint issues an access token only, and Vexa can never sync again once it expires).
5. Under **Certificates & secrets**, create a **client secret** and copy its value immediately —
   Azure never shows it again.
6. Copy the **Application (client) ID** and the client secret into admin-api's environment:

```bash
MICROSOFT_CALENDAR_CLIENT_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
MICROSOFT_CALENDAR_CLIENT_SECRET=xxxxxxxxxx
MICROSOFT_CALENDAR_REDIRECT_URI=https://dashboard.example.com/calendar/microsoft/callback
```

`CALENDAR_TOKEN_ENCRYPTION_KEY` (set once, above, for Google) is shared — the same AES-256-GCM key
`token_cipher.py` encrypts every stored Google **and** Microsoft refresh token with, bound to the
user id and connection id; a deployment with no Google connection still needs it set for Microsoft
to connect.

Unset any of the three Microsoft keys and the three Microsoft routes
(`GET /user/calendars/microsoft/authorize`, `POST /user/calendars/microsoft/exchange`, and the
internal `POST /internal/calendars/{id}/microsoft-token`) answer a typed `503` naming exactly
what's missing; the ICS calendar surface and the Google connector are completely unaffected.

## Connect with a secret ICS address

Any calendar whose provider does not support the Google or Microsoft OAuth flows above — or a
Google/Microsoft account an admin has not enabled OAuth for — connects off its **secret ICS
address** instead: no OAuth, no calendar permissions.

### 1. Find your secret ICS address

<Tabs>
  <Tab title="Google Calendar">
    1. Open [Google Calendar settings](https://calendar.google.com/calendar/r/settings) → pick your
       calendar under **Settings for my calendars**.
    2. Scroll to **Integrate calendar**.
    3. Copy **Secret address in iCal format** — it looks like
       `https://calendar.google.com/calendar/ical/you%40company.com/private-…/basic.ics`.

    <Warning>
    **Not** the field above it. The *Public address in iCal format* (`…/public/basic.ics`) only
    works for calendars you've made fully public — for a normal private calendar Google answers
    it with `401`/`404`, and Vexa will show you exactly that error. The *Public URL* and *Embed
    code* are web pages, not feeds — pasting one is rejected at save with a pointer back here.
    </Warning>

    <Accordion title="No 'Secret address in iCal format' field? (Google Workspace)">
    On a **Google Workspace** domain the secret address is governed by an admin policy, and under
    the Workspace default (*"Only free/busy information"*) Google **hides the field entirely** —
    the section ends at the public address. A Workspace admin unlocks it domain-wide:

    1. [admin.google.com](https://admin.google.com) → **Apps → Google Workspace → Calendar**
    2. **Sharing settings** → **External sharing options for primary calendars**
    3. Select **"Share all information, but outsiders cannot change calendars"** and save.

    Propagation usually takes minutes (Google says up to 24 h). Reload the calendar settings page
    and the **Secret address in iCal format** field appears below the public one.

    This only enables the *possibility* of detailed external sharing — nothing is exposed until a
    user actually hands out their secret address, and each address is revocable per calendar
    (**Reset** next to the field).
    </Accordion>
  </Tab>
  <Tab title="Outlook / Microsoft 365">
    1. Outlook on the web → **Settings → Calendar → Shared calendars**.
    2. Under **Publish a calendar**, pick your calendar, permissions **Can view all details**, and
       click **Publish**.
    3. Copy the **ICS** link.
  </Tab>
</Tabs>

<Warning>
The ICS address is a **secret** — anyone holding it can read your calendar. Vexa stores it
accordingly: it is never shown back in full (reads return a masked form), and the sync fetch runs
through the same server-side request guard as webhooks. Revoke it anytime from your calendar's
settings ("Reset" in Google Calendar) — then reconnect with the new address.
</Warning>

### 2. Connect it — and get an answer immediately

On hosted Vexa, the dashboard lives at **[dashboard.vexa.ai](https://dashboard.vexa.ai)** — a
different host from `vexa.ai`, which carries the site and sign-in and has no calendar surface. Sign
in there, open **Add Bot**, and switch to the **Calendar** tab — **Other calendar (ICS)** is the
fallback below **Connect Google Calendar**. Give the connection a recognizable name such as **Work**
or **Personal**, paste the secret address, choose whether meetings from that calendar should
auto-join, and click **Connect**. Repeat this for each feed you want Vexa to follow (up to 10 active
connections).

Everything the dashboard does here is the [calendar API](/api/calendar) underneath, so a self-hosted
deployment — which ships the API but not the hosted dashboard — connects feeds the same way with
`POST /user/calendars`. The API is the complete surface; the examples are below.

Each calendar has its own **Default bot name**, used when that calendar arms an unattended join.
For a meeting present in several calendars, the first source with auto-join enabled supplies the bot
name. A dedicated **Upcoming** page grouping auto-joins by source calendar is separate,
not-yet-shipped dashboard work.

**Connecting runs a sync on the spot** — within seconds the panel answers with the result, not
silence:

- `✓ Synced just now — imported 3` — done; the meetings are under **Upcoming**.
- `✓ Synced just now — 0 imported, 0 updated` — the feed is fine and already reconciled, or it has
  no event inside the current import window.
- `⚠ Last sync failed: …` — the actual reason, named (see the
  [error reference](#reading-the-sync-status) below).

Each connection keeps its own **last sync status**, **Auto-join** switch, **Sync now**, and
**Disconnect** action — no waiting on the background cycle after you add an event or change a
preference.

### How often Vexa checks the feed

- **Connect and Sync now:** run the same reconciliation immediately.
- **Hosted calendar rollout:** polls each connected feed every **60 seconds**.
- **Self-hosted default:** polls every **5 minutes**. Operators can change this with
  `CALENDAR_SYNC_INTERVAL_S`.
- **Bot scheduling:** checks due planned meetings every **30 seconds** by default. A bot becomes
  eligible **60 seconds before** `scheduled_at` and remains eligible until **10 minutes after** it.

The calendar provider controls when an edit appears in its published ICS feed, so the practical
delay is provider publication time plus up to one Vexa polling interval. Sync now cannot make an
edit visible before Google or Outlook has published it to the feed.

Over the API:

```bash Connect a named feed
curl -X POST "$API_BASE/user/calendars" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"name":"Work","ics_url":"https://calendar.google.com/calendar/ical/…/private-…/basic.ics","auto_join":true,"bot_name":"Work Notes"}'
```

```bash Sync right now → the fresh result
curl -X POST "$API_BASE/user/calendars/$CALENDAR_ID/sync" -H "X-API-Key: $API_KEY"
# {"calendar_id":"…","calendar_name":"Work","last_sync":"2026-07-08T15:30:00+00:00","last_error":null,"counts":{"created":3,"updated":0,"cancelled":0}}
```

```bash Read the last sync status
curl "$API_BASE/user/calendars/$CALENDAR_ID/sync" -H "X-API-Key: $API_KEY"
```

`GET /user/calendars` lists the masked connections. The original `/user/calendar` endpoint remains
available for single-calendar clients and refers to the first active connection. The singular
`/user/calendar/sync` compatibility endpoint synchronizes all active connections and returns an
aggregate stamp. See the [Calendar API](/api/calendar) for exact schemas and statuses.

Legacy single-calendar clients can still set or read the user-wide fallback bot name through the
compatible singular preferences edge:

```bash Set the default auto-join bot name
curl -X PUT "$API_BASE/user/calendar" \
  -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"bot_name":"My Meeting Notes"}'
```

### Multi-calendar API reference

| Operation | Endpoint | Result |
|---|---|---|
| List connections | `GET /user/calendars` | Every connection (ICS, Google, and Microsoft), masked: an ICS row never returns its feed URL, a Google/Microsoft row never returns its refresh token. |
| Connect (ICS) | `POST /user/calendars` | Creates one ICS connection from `name`, `ics_url`, `auto_join`, and optional `bot_name`. |
| Get Google consent URL | `GET /user/calendars/google/authorize` | Returns `{"authorize_url": "...", "state": "..."}` — redirect the browser to `authorize_url`. |
| Complete Google connect | `POST /user/calendars/google/exchange` | Body `{"code", "state"}` from Google's redirect (DB-31's callback page relays these). Exchanges the code, stores the connection, returns it masked. |
| Get Microsoft consent URL | `GET /user/calendars/microsoft/authorize` | Returns `{"authorize_url": "...", "state": "..."}` — redirect the browser to `authorize_url`. |
| Complete Microsoft connect | `POST /user/calendars/microsoft/exchange` | Body `{"code", "state"}` from Microsoft's redirect (the dashboard's callback page relays these). Exchanges the code, stores the connection, returns it masked. |
| Rename or configure | `PATCH /user/calendars/{calendar_id}` | Updates `name`, `auto_join`, `bot_name`, `enabled` (+ `ics_url` for an ICS connection) for only that connection. |
| Disconnect | `DELETE /user/calendars/{calendar_id}` | Removes that source without changing other connections. |
| Read sync state | `GET /user/calendars/{calendar_id}/sync` | Returns that connection's latest sync stamp. |
| Sync now | `POST /user/calendars/{calendar_id}/sync` | Fetches and reconciles only that connection immediately. |

A masked connection now carries `"kind": "ics"`, `"kind": "google"`, or `"kind": "microsoft"`. A
Google connection's shape adds `google_email` (the connected account, not a secret),
`google_calendar_ids` (default `["primary"]`), and `reconnect_needed`; a Microsoft connection adds
the same shape under `microsoft_email` / `microsoft_calendar_ids`. `reconnect_needed` is `true`
once the provider reports the grant revoked or expired, `false` otherwise; the dashboard's Calendar
tab shows **Reconnect needed** and a **Reconnect** action for a Google connection in this state
today. A Microsoft connection made directly through the API carries the same `reconnect_needed`
field, but the dashboard's own **Reconnect** control for it ships alongside DB-32's dashboard
button above.

Imported meeting metadata includes `data.calendar_sources`, an array of source objects with the
stable connection `id`, display `name`, provider event `uid`, source `auto_join` preference,
per-calendar `bot_name`, and the complete event snapshot. Consumers should use the array rather
than the single-source convenience fields when they need complete provenance.

## What Vexa stores

Vexa does not keep a second calendar-event database. A connected feed and an imported meeting
have separate storage responsibilities:

| Data | Durable home | Notes |
|---|---|---|
| Named calendar connections, secret ICS URLs, per-feed auto-join, per-feed bot name | The user's `data` JSON document in Postgres | User-facing reads mask the feed URL. The full URL crosses only the authenticated internal sync edge. |
| Google or Microsoft connection's refresh token | The same `data` document, **encrypted at rest** (`token_cipher.py`'s AES-256-GCM, keyed by `CALENDAR_TOKEN_ENCRYPTION_KEY`, bound to the user id and connection id) | Never stored in the clear, never returned by any read, never sent to meeting-api — only admin-api decrypts it, to mint a short-lived access token over its own internal edge. |
| Imported events | Ordinary rows in the Postgres `meetings` table | A future event is a planned meeting with `status: "scheduled"`. |
| Event and calendar provenance | The meeting's `data` JSON document | Includes scheduling, attendees, calendar source IDs/names, and provider event UIDs. |
| Latest sync time, error, and created/updated/cancelled counts | Redis | Operational status under the user/connection sync key; this is not the durable event authority. |
| Bot attempts | The same meeting row plus `meeting_sessions` rows | Auto-join claims the planned meeting in place through the normal bot lifecycle. |
| Transcript segments | Postgres `transcriptions` rows linked to the meeting | Finalized meeting output remains addressable by the meeting ID. |
| Recording and processed post-meeting metadata | The meeting's `data` JSON document | Media objects themselves use the configured object store. |

An imported meeting currently carries this calendar-specific shape (alongside its ordinary meeting
fields):

```json
{
  "status": "scheduled",
  "data": {
    "scheduled_at": "2026-08-14T15:00:00+00:00",
    "calendar_uid": "provider-event-uid",
    "calendar_connection_id": "calendar-uuid",
    "calendar_name": "Work",
    "calendar_managed": true,
    "calendar_sources": [
      {
        "id": "calendar-uuid",
        "name": "Work",
        "uid": "provider-event-uid",
        "auto_join": true,
        "bot_name": "Work Notes",
        "event": {
          "resolved_start": "2026-08-14T15:00:00+00:00",
          "calendar": {
            "name": "VCALENDAR",
            "properties": {
              "VERSION": [{"value": "2.0"}],
              "PRODID": [{"value": "-//Provider//Calendar//EN"}]
            }
          },
          "component": {
            "name": "VEVENT",
            "properties": {
              "UID": [{"value": "provider-event-uid"}],
              "ORGANIZER": [{
                "value": "mailto:owner@example.com",
                "parameters": {"CN": "Owner"}
              }],
              "X-PROVIDER-FIELD": [{"value": "provider-value"}]
            }
          }
        }
      }
    ],
    "attendees": [
      {
        "email": "person@example.com",
        "name": "Person",
        "partstat": "accepted"
      }
    ]
  }
}
```

`calendar_sources` is the authoritative multi-calendar provenance. The singular
`calendar_connection_id`, `calendar_name`, and `calendar_uid` fields are compatibility conveniences
for the first source.

### Participants and current metadata boundary

ICS `ATTENDEE` entries are synchronized into `data.attendees`. Vexa preserves the normalized email,
optional display name, and participation status (`partstat`, such as `accepted` or `tentative`) for
ordinary people. Calendar rooms and resources are excluded from this convenience list, but remain
present in the complete event snapshot. Attendee additions, removals, and response changes follow
the feed while the meeting is still planned.

The per-source `event` snapshot preserves every event property in its canonical iCalendar text
representation, including every property parameter, repeated property, provider `X-` extension,
and nested component such as `VALARM`. It also preserves the top-level `VCALENDAR` properties. For
a moved or otherwise overridden recurring occurrence, `event.component` is the selected occurrence
and `event.series_master` retains the RRULE master. `event.resolved_start` is the UTC occurrence Vexa
actually scheduled.

This is a JSON-safe event snapshot, not the original feed: it deliberately does not contain the
secret ICS URL or unrelated events. Vexa normalizes the commonly queried title, start, meeting link,
and people into ordinary meeting fields while retaining the complete source component for consumers
that need organizer, description, location, end time, recurrence, sequence, revision, categories,
custom provider properties, or other calendar metadata.

## Reading the sync status

Every failure names its fix — these are the messages the panel (and the API stamp's `last_error`)
can show:

| Message | What it means | Fix |
|---|---|---|
| `the URL answered HTTP 401` / `HTTP 404` | You pasted the **public** iCal address of a private calendar. | Use the **secret** address (`…/private-…/basic.ics`). |
| `the URL returns a web page, not a calendar feed` | An embed/share *page* URL, not a feed. (Google's embed page is also rejected at save.) | Copy the address from **Integrate calendar**, not the browser's address bar. |
| `the URL redirects — paste the final feed URL` | The address bounces through a redirect; the guarded fetch doesn't follow them. | Paste the URL the redirect lands on. |
| `the URL doesn't return an ICS calendar (no BEGIN:VCALENDAR)` | The server answered, but not with calendar data. | Check you copied the full `.ics` address. |
| `the feed is too large (over 2 MB)` | Unusually huge feed. | Sync a specific calendar rather than an aggregate. |
| `couldn't reach the URL (unreachable, timed out, or a blocked/internal address)` | Network failure, or the address points somewhere the server-side guard refuses (internal hosts). | Verify the URL opens from a browser; use the calendar provider's public host. |

A Google or Microsoft connection shows one more, distinct state rather than a generic failure:

| State | What it means | Fix |
|---|---|---|
| `reconnect_needed: true` (panel: **Reconnect needed**) | The provider reported the grant revoked or expired (`invalid_grant`) — access was removed at [myaccount.google.com/permissions](https://myaccount.google.com/permissions) or [myaccount.microsoft.com](https://myaccount.microsoft.com/), the OAuth client was deleted, or a very long idle period expired it. | Click **Reconnect** — the same consent flow, which clears the flag on success. |

## What imports (and what doesn't)

- **Events with a recognizable meeting link** — Meet, Zoom, or Teams, found in the event's
  conferencing field, location, or description — can auto-join. Link-less events still appear as
  planned calendar entries, but Vexa has nowhere to send a bot until a meeting link is added.
- **One meeting per event — the next occurrence only.** A recurring series tracks its next
  upcoming occurrence; the one after imports once the current completes.
- **Moves and cancellations follow the feed.** A rescheduled event moves its meeting; a cancelled
  or deleted event removes it. Title, start time, meeting link, and attendee changes are also
  reconciled while the row remains planned. Once the bot lifecycle claims the meeting (requested,
  active, completed, or failed), calendar sync never rewrites that live or historical record.
- **Your manual plans are respected.** If you already planned a meeting on the same link, the
  calendar event links up with it instead of creating a duplicate — your title and workspace
  binding win.
- **One meeting can have several sources.** If Work and Personal contain the same native meeting,
  Vexa keeps one meeting and records both named calendar sources. The meeting detail page shows
  them under **Imported from**.

## Auto-join for imported meetings

Every calendar connection has its own **Auto-join** switch and **Default bot name**. A meeting
shared by multiple connected feeds auto-joins when at least one source has auto-join enabled; the
first auto-joining source in stable source order supplies its bot name. You can still override
auto-join per meeting in its prep view. Connections created without an explicit bot name default
to the legacy user-wide setting, then `Vexa`.

## Disconnect

On the Calendar tab, choose **Disconnect** for the exact named feed. Meetings that also belong to
another calendar keep that source and remain. A future planned meeting owned only by the removed
calendar is cleaned up; a manual plan that the calendar had adopted remains. Other connections
and their credentials are untouched.
