<Note>
Self-host only if you intend to **sell** subscriptions — a self-host that gives every account the
Free plan for free needs none of this. The endpoints below answer a typed **503** naming exactly
what's missing until you configure Stripe (see [Deploy this yourself](#deploy-this-yourself)).
</Note>

Vexa's plan catalog (Free / Pro / Team — meetings/month, minutes/meeting, concurrent bots, recording
retention, AI summaries) lives in one file:
`core/identity/services/admin-api/src/admin_api/app/billing/catalog.py`. A user's subscription state
— tier, status, renewal — lives on their own account row and is resolved into limits + usage by
`GET /user/entitlements`. This page covers the three endpoints that keep that state true: **Checkout**
(buy), **Portal** (manage), and the **webhook** (the only thing that ever writes it).

**Don't have a key yet?** Hosted: sign in at [vexa.ai/signin](https://vexa.ai/signin) with a Google
account and copy your key from [your account page](https://vexa.ai/account) — free credit, no card
required. Self-hosted: `make all` prints a key when the stack comes up.

## Start a subscription

```bash
curl -X POST -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"plan": "pro", "interval": "month"}' \
  "$API_BASE/billing/checkout"
```

`plan` is `pro` or `team` (never `free` — there is nothing to buy to get it); `interval` is `month`
or `year`. The response is `{"url": "https://checkout.stripe.com/..."}` — redirect the person there.
The FIRST checkout for an account creates its Stripe customer and stores the id; every later
checkout or portal call reuses it. A `(plan, interval)` this deployment does not sell (no matching
`STRIPE_PRICE_*` configured) answers 503 naming the missing key, never a guessed price.

**One subscription per account.** Checkout asks Stripe for the customer's subscriptions first and
answers **409** while one is still live (`active`, `trialing`, `past_due`, `unpaid`,
`incomplete` or `paused`) — a subscriber changes plan with `POST /billing/change` below instead
of buying a second one. Once a subscription has ended, checkout works again.

## Confirm a purchase on return from Checkout

```bash
curl -X POST -H "X-API-Key: $API_KEY" "$API_BASE/billing/sync"
```

Records the caller's subscription as Stripe holds it right now — the same re-read and write the
webhook does — and answers `{"active": true}` once a live subscription is on record. The
dashboard calls it when Stripe Checkout sends the person back to `?checkout=success` (retrying
for about half a minute), so the page says "Payment received — you're on Pro monthly" without
waiting for webhook delivery. The newest live subscription wins; with none live, the stored one is
re-read, so an ended subscription is recorded too. A caller with no Stripe customer gets
`{"active": false}` and nothing reaches Stripe. The webhook stays the writer for everything that
happens later (renewals, failed payments, cancellations in the portal).

A Stripe customer deleted in the Stripe dashboard is noticed on the next checkout (a new customer
is created) or portal call (answered as "no customer yet").

## Switch plans

```bash
curl -X POST -H "X-API-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{"plan": "team", "interval": "month"}' \
  "$API_BASE/billing/change"
```

Changes the caller's one subscription in place and answers `{"effective": "now" | "scheduled" | "kept"}`:

| From → to | Takes effect | Charged |
|---|---|---|
| Upgrade, same interval (Pro → Team) | **now** | nothing now; the next renewal bills the new price |
| Downgrade (Team → Pro) | at the end of the paid period (**scheduled**) | the new price from that renewal |
| Monthly ↔ yearly, same plan | at the end of the paid period (**scheduled**) | the new price from that renewal |
| Upgrade and interval change (Pro monthly → Team yearly) | the better plan **now** at the current interval; the new interval at renewal | nothing now; Team yearly from that renewal |
| The plan and interval it already has | a pending switch is called off (**kept**) | — |

Stripe cannot move a subscription between monthly and yearly mid-period without invoicing it
there and then, so an interval switch always waits for the period to end. A switch that waits is
held in Stripe as a subscription schedule; `GET /user/entitlements` reports it under
`subscription.pending_change` (`{plan, interval, at}`), alongside the plan and interval the
subscription bills now (`subscription.plan`, `subscription.interval`).

A caller with no live subscription gets **409** (check out first). A subscription set to cancel at
the end of its period gets **409** too — resume it in the portal before switching. When Stripe
refuses a call, the route answers **502** with Stripe's own reason in `detail`.

<Note>
In the Stripe Customer Portal settings, turn **off** plan switching and cancellation, and keep
payment method and invoices: switching and cancelling have their own routes (above and below),
and a change made in the portal bypasses their rules. The webhook still records whatever Stripe
reports either way.
</Note>

## Show the prices

```bash
curl -H "X-API-Key: $API_KEY" "$API_BASE/billing/prices"
```

```json
{"prices": [
  {"plan": "pro", "interval": "month", "unit_amount": 500, "currency": "usd"},
  {"plan": "pro", "interval": "year", "unit_amount": 5000, "currency": "usd"}
]}
```

Every configured `STRIPE_PRICE_*` (the plan → price mapping below), read back from
Stripe: `unit_amount` is in the currency's minor units, exactly as Stripe stores it. Nothing in
Vexa holds an amount, so the figure shown before Checkout is the figure Checkout charges. A
complete read is cached for five minutes; a price you edit in Stripe shows within that window.

A price is **left out**, and a warning names it in admin-api's log, when Stripe won't return it,
when it's archived, when it has no fixed amount, or when Stripe bills it on a different interval
than the env var it's configured under (a yearly price pasted into `STRIPE_PRICE_PRO_MONTHLY`).
The dashboard then shows that plan without a figure; checkout for it is unaffected by this route.

## Cancel, and resume

```bash
curl -X POST -H "X-API-Key: $API_KEY" "$API_BASE/billing/cancel"
curl -X POST -H "X-API-Key: $API_KEY" "$API_BASE/billing/resume"
```

`/billing/cancel` ends the caller's subscription when its paid period ends and answers
`{"ends_at": "<iso8601>"}`. Until then the plan stays in force — `GET /user/entitlements` reports
`will_renew: false` and `subscription.cancel_at_period_end: true` — and Stripe charges nothing
more; at period end Stripe ends it and the account resolves to Free. A pending plan switch is
called off by the cancellation. `/billing/resume` calls the cancellation off before the period
ends (`{"ends_at": null}`), and the subscription renews as before. A cancelling subscription
can't be switched until it is resumed. Both answer **409** without a live subscription.

## Payment method and invoices

```bash
curl -X POST -H "X-API-Key: $API_KEY" "$API_BASE/billing/portal"
```

Returns `{"url": "https://billing.stripe.com/..."}` — Stripe's own hosted portal for card changes
and invoice history. Card data never touches Vexa's servers. A caller with no Stripe customer yet
(never checked out, or one deleted in Stripe) gets a **409** — checkout first.

## Read the resolved plan

```bash
curl -H "X-API-Key: $API_KEY" "$API_BASE/user/entitlements"
```

Returns the resolved plan, its limits, the current billing period, and usage so far this period —
`plan_id`, `status`, `limits`, and `usage`. This is what `POST /bots`' quota enforcement reads; a
`past_due` subscription keeps its paid tier for a 7-day
grace window before falling back to Free. A subscription set to cancel at the end of its period
is still `active` (with `will_renew: false`) and keeps its tier until then; `canceled` means
Stripe has ended it, and resolves to Free.

`limits.max_minutes_per_meeting` (Free 60, Pro/Team 240) is the OTHER cap `POST /bots` enforces,
alongside the monthly meeting quota — every bot's active phase is hard-capped at that many minutes,
taking the SHORTER of it and any `automatic_leave.max_bot_time` the request itself passes. The bot
leaves with `completion_reason: max_bot_time_exceeded` when it hits the cap either way — see
[completion reasons](/troubleshooting/completion-reasons#the-per-plan-minute-cap) for how the two
combine and what to do about it.

## Sign-up: the trial-abuse floor

`POST /admin/users` — the one point a person is created (every sign-in path onboards through it,
including the dashboard's own find-or-create) — refuses a disposable/throwaway email domain:

```json
{"error": "disposable_email_domain", "message": "This email domain is a disposable/throwaway provider and cannot be used to sign up. Use a permanent email address."}
```

as a typed **422**. What a person actually sees differs by sign-in door, and neither surfaces this message today
(dashboard-side follow-up, not part of this change): the OAuth callback
(`clients/dashboard/src/app/api/auth/authOptions.ts`) treats any `findOrCreateUserToken` failure
alike — it logs `result.error` server-side and returns `false` from `signIn`, which NextAuth
turns into a generic redirect to `/login` with no reason exposed; the dev email-login door
(`api/auth/login/route.ts`) is closer but still rough — it forwards `result.error` verbatim as
`{error: result.error}`, and `result.error` is `adminRequest`'s raw response *text*, i.e. the
whole JSON body `{"error":"disposable_email_domain","message":"..."}` as one string, not the
`message` field alone.

The domain list (`admin_api/data/disposable_email_domains.txt`) is vendored from
[disposable-email-domains/disposable-email-domains](https://github.com/disposable-email-domains/disposable-email-domains)
(CC0 1.0 — ADR-0004 Category A). Matching is registrable-domain-and-subdomains, case-insensitive:
`user@sub.mailinator.com` matches a listed `mailinator.com`. Two env overrides, both read live
(no redeploy to change either):

- `SIGNUP_ALLOW_DISPOSABLE=true` — disables the block entirely.
- `SIGNUP_DISPOSABLE_EXTRA_DOMAINS=foo.test,bar.test` — blocks additional domains the vendored
  list hasn't caught up to yet, on top of it.

**An address that already has an account is never affected** — the check only runs on the INSERT
branch of `create_user`; the existing-row lookup that make find-or-create idempotent returns
first, before the domain is ever checked, for every request against an address already onboarded.

Every call to `POST /admin/users` also logs the domain and the client address the request
carries, for abuse review — **never to block**, only to log:

```
signup: email_domain=mailinator.com ip=203.0.113.7
```

**What that IP actually is, stated honestly:** this route is called by the dashboard's own
Next.js server, not directly by a browser, and that call does not currently forward any
`X-Forwarded-For` header — so today the logged address is the dashboard server's own address
(its container/pod IP or a reverse proxy in front of admin-api), not the signing-up person's
browser. The dashboard already resolves a real client address for its own rate limiter, gated on
`DASHBOARD_TRUST_PROXY` (`clients/dashboard/src/lib/rateLimit.ts`); it is not yet threaded
through to the account-creation call. `_signup_client_ip` in `app/main.py` reads
`X-Forwarded-For` first if a future dashboard change starts sending it, so wiring that through is
a dashboard-side change with no core change needed.

**The Free allowance belongs to verified identities.** Each sign-in door records how it proved the
address, in the account's `users.data` under `identity`:
`{"provider": "google" | "microsoft" | "email", "email_verified": true | false, "verified_at": "<iso8601>"}`
(`verified_at` only when verified). The dashboard sends it at sign-in: Google reports
`email_verified` in its profile; a Microsoft sign-in counts as verified; the development email door
(`DASHBOARD_ALLOW_EMAIL_LOGIN`) proves nothing and records `email_verified: false`. It rides on
`POST /admin/users` (`identity_provider` + `email_verified`, supplied together, provider one of the
three above) and, for an existing account, on `PATCH /admin/users/{id}` with the same two fields.
A recorded `email_verified: true` is never downgraded by a later, weaker sign-in.

An account whose record says `email_verified: false` resolves on the Free plan with **0 included
meetings**, and `reason: "identity_unverified"` appears on `GET /user/entitlements` and in the
`402` `quota_exceeded` body of `POST /bots` (the dashboard shows fixed copy for it: sign in with
Google or Microsoft to verify, or upgrade). An account with **no** record — created before the record
existed, or through the terminal or the API — is unchanged. Paid plans and a `plan_override` win over
the rule; a `quota_bonus` adds to the zero. Signing in again through Google or Microsoft upgrades
the record.

## Dunning and grace (a payment fails)

`invoice.payment_failed` moves a subscription to `subscription_status: past_due`. `resolve_plan`
(`billing/entitlements.py`) still resolves it to its **paid** tier for a **7-day grace window**
— `grace_until`, `period_end` plus `PAST_DUE_GRACE_DAYS` — so a card that failed once does not
immediately drop the account to Free. `GET /user/entitlements` reports `status: "past_due"` and
`grace_until` for the whole window; after `grace_until` passes with no successful payment, the
SAME resolver falls back to Free limits automatically — nothing deletes the account's existing
meetings, recordings or transcripts either way; only the plan's limits change.

The webhook sends **one email** per failed invoice, through the flows mailbox, to the address on
the account: a plain notice that a payment failed and a link to `/billing` on your dashboard
(`VEXA_FLOWS_DASHBOARD_URL`, the same env var [the meeting-ready mail](/how-to/post-meeting-report)
already reads) — no price, no due amount, no legal language, because `billing/catalog.py` is not
consulted for it. It is idempotent on the **invoice**, not the Stripe event id: a redelivered
webhook event and a fresh Stripe retry of the same unpaid invoice both resolve to the same fact
id on the flows side, so however many times Stripe redelivers or retries, exactly one mail goes
out per failed invoice. A deployment with no flows domain configured sends no mail and drops
nothing else — the plan resolution above is unaffected either way.

### Retention purge for a lapsed Free-plan recording

Free's `recording_retention_days` (`billing/catalog.py` — 7 days today) is enforced by an
opt-in background sweep on **meeting-api**, `RETENTION_SWEEP_ENABLED=true`
(`meeting_api/sweeps/retention.py`). Each tick reads the Free plan's current retention ceiling
live off admin-api's catalog (never hardcoded on meeting-api), scans the oldest terminal meetings
in a bounded batch (`RETENTION_SWEEP_BATCH_LIMIT`, default 200), and — for each candidate
recording whose owner is **currently** resolved to Free (checked per distinct owner through the
same `/internal/users/{id}/bot-context` edge `POST /bots` already calls) and whose own age is
past the ceiling — deletes it through the exact same owner-scoped path a person's own
`DELETE /recordings/{id}` uses: storage objects first, then the JSONB row. A Pro/Team recording,
or a Free user still inside their `past_due` grace window (which resolves to the PAID plan, not
Free — see above), is left alone. Disabled by default; see `config.v1.json` on meeting-api for
`RETENTION_SWEEP_ENABLED` / `RETENTION_SWEEP_INTERVAL_S` / `RETENTION_SWEEP_BATCH_LIMIT`.

## How the webhook keeps this true

`POST /billing/webhook` is the **only** writer of a user's Stripe fields. It never trusts a
delivered event's own body for what to write: on `checkout.session.completed`,
`customer.subscription.created|updated|deleted`, and `invoice.payment_failed|paid`, it resolves
which Stripe **subscription** the event concerns and re-reads that subscription's **current**
state from the Stripe API before writing anything. That makes a redelivery a no-op and makes two
events arriving **out of order** converge on the same answer regardless of which is processed
last — the alternative (trusting each event's own snapshot) can let a stale "updated" event
resurrect a subscription Stripe has already canceled.

Authentication is the `Stripe-Signature` header alone (HMAC-SHA256 over the timestamped raw body,
constant-time compared, a 300-second tolerance) — Stripe cannot present an API key, so this route
carries none of the usual `X-API-Key` scoping. **Where this route is reachable from the public
internet is a per-deployment decision this page does not make for you** — see
[Deploy this yourself](#deploy-this-yourself).

A price id that doesn't match any `STRIPE_PRICE_*` you've configured is logged and ignored —
`users.data` is left exactly as it was, never guessed at.

## The plan → price mapping

One file decides what a price id means: `billing/catalog.py`'s `STRIPE_PRICE_ENV` maps
`(plan, interval)` to the env var carrying that price's Stripe id. Nothing in this codebase
hardcodes a `price_...` literal — every plan a deployment sells is one env var away.

| Plan / interval | Env var |
|---|---|
| Pro / monthly | `STRIPE_PRICE_PRO_MONTHLY` |
| Pro / yearly | `STRIPE_PRICE_PRO_YEARLY` |
| Team / monthly | `STRIPE_PRICE_TEAM_MONTHLY` |
| Team / yearly | `STRIPE_PRICE_TEAM_YEARLY` |

Leave one unset and that combination simply isn't for sale — `POST /billing/checkout` for it
answers 503 naming the env var, rather than falling back to a different plan or a wrong price.

## Support comps (admin overrides)

Sometimes support needs to comp a user outright, without touching Stripe: bump them to a plan
they haven't paid for, or hand them one extra meeting this period. `PATCH /admin/users/{id}`
(admin tier, `X-Admin-API-Key`) carries two fields for exactly that:

```bash
curl -X PATCH -H "X-Admin-API-Key: $ADMIN_KEY" -H "Content-Type: application/json" \
  -d '{"plan_override": "team", "quota_bonus": 1}' \
  "$ADMIN_API_BASE/admin/users/42"
```

- **`plan_override`** — a catalog plan id (`free`, `pro`, `team`) that wins over whatever Stripe
  resolved the user's tier to. Send `null` to clear it and let the Stripe-derived tier decide
  again. An id `billing/catalog.py`'s `PLANS` doesn't recognize is a **422**.
- **`quota_bonus`** — a non-negative integer, extra meetings added to `meetings_per_month` for
  **this resolved period only**. Send `null` to clear a previously-set bonus. A negative value is
  a **422**. There is no "sticky, renews every period" mode: a bonus is stamped with the period it
  was granted for (`quota_bonus_period_start`, set automatically to the user's current resolved
  period when you set `quota_bonus` — you never supply the timestamp yourself) and simply does
  not apply once that period ends. This is deliberate — the simplest honest design is a comp tied
  to the period support meant it for, never one that silently keeps giving every month until
  someone remembers to take it back. Comp a recurring case by re-sending `quota_bonus` each period.
  A bonus is irrelevant (never added) on a plan whose `meetings_per_month` is already unlimited
  (Pro, Team, or a plan reached via `plan_override`).

Both fields are applied inside `resolve_plan` — the SAME resolver `GET /user/entitlements`,
`POST /internal/validate` (the gateway's `x-user-limits`), and `/internal/users/{id}/bot-context`
(the spawn-time quota check `POST /bots` and calendar auto-join both go through) all call. One
PATCH is visible everywhere at once: a `plan_override` to `team` immediately raises the user's
concurrent-bot cap and lifts their monthly meeting quota, and a `quota_bonus` immediately shows up
in the next spawn attempt's quota check — there is no second place either has to be told about.

`GET /user/entitlements` echoes both back (`plan_override`, `quota_bonus_applied`) so a comped
user's own page can say why their plan or allowance differs from what Stripe alone would resolve
to, and `GET /admin/users/{id}` returns the raw stored fields (`data.plan_override`,
`data.quota_bonus`, `data.quota_bonus_period_start`) for support tooling. The terminal's hidden
admin panel (Infra → Users tab) wraps this PATCH in a small form: look a user up by email, set the
two fields (and `max_concurrent_bots`, the pre-billing per-user cap — see
`billing/catalog.py`'s `effective_concurrent_cap` for how the two combine), save.

## Deploy this yourself

### 1. In the Stripe dashboard

1. **Products & prices** — create one Product per paid plan (Pro, Team), each with a **monthly**
   and a **yearly recurring Price**. Copy each Price id (`price_...`) into the matching
   `STRIPE_PRICE_*` env var above.
2. **Customer Portal** ([dashboard.stripe.com/settings/billing/portal](https://dashboard.stripe.com/settings/billing/portal))
   — enable it and turn on the features you want self-serve (cancel, update payment method,
   view invoices). Vexa creates the session; Stripe renders the page.
3. **Webhook endpoint** ([dashboard.stripe.com/webhooks](https://dashboard.stripe.com/webhooks)) —
   add an endpoint pointing at your deployment's `POST /billing/webhook` and select exactly these
   events: `checkout.session.completed`, `customer.subscription.created`,
   `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`,
   `invoice.paid`. Copy the endpoint's **Signing secret** (`whsec_...`) into
   `STRIPE_WEBHOOK_SECRET`.
4. Copy your account's **Secret key** (`sk_...`, Developers → API keys) into `STRIPE_SECRET_KEY`.

<Warning>
`POST /billing/webhook` needs to be reachable from Stripe's servers. admin-api itself binds
`127.0.0.1` only in the standard Docker Compose deploy (see [Deployment](/deployment)) — it is
**not** fronted by the gateway for this one route, because every gateway route requires an
`X-API-Key` and Stripe cannot present one. Exposing this endpoint (a dedicated reverse-proxy path
straight to admin-api, or another ingress shape) is a decision to make for your own deployment;
this page intentionally does not prescribe one. Until it's wired up, checkout and the portal work
end to end but a completed purchase will not update the buyer's plan — test with the
[Stripe CLI](https://stripe.com/docs/stripe-cli) (`stripe listen --forward-to
localhost:18057/billing/webhook`) against a local admin-api port in the meantime.
</Warning>

### 2. On the deployment

Set on **admin-api** (`deploy/compose/.env` for Docker Compose):

```bash
STRIPE_SECRET_KEY=sk_live_...
STRIPE_WEBHOOK_SECRET=whsec_...
STRIPE_CHECKOUT_SUCCESS_URL=https://your-host.example.com/settings/billing?checkout=success
STRIPE_CHECKOUT_CANCEL_URL=https://your-host.example.com/settings/billing?checkout=cancelled
STRIPE_PORTAL_RETURN_URL=https://your-host.example.com/settings/billing
STRIPE_PRICE_PRO_MONTHLY=price_...
STRIPE_PRICE_PRO_YEARLY=price_...
STRIPE_PRICE_TEAM_MONTHLY=price_...
STRIPE_PRICE_TEAM_YEARLY=price_...
```

Any of `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` / the three URLs left unset takes down all
eight `/billing/*` routes with a 503 naming what's missing — the rest of the deployment is
unaffected. An unset `STRIPE_PRICE_*` only takes down checkout for that one plan/interval. See
also `BILLING_UPGRADE_URL` on the same service — the page a `quota_exceeded` refusal (from
`POST /bots` when a Free user is over their monthly meeting) points them at, typically this same
billing page.
